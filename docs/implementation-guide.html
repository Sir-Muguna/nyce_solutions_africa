NYCE SOLUTIONS catalogue — Odoo implementation guide

A practical map from the static GitHub Pages catalogue (index.html / standalone/nycesolutionssafrica-refactored.html) to an Odoo Website + eCommerce build. Customer copy lives in the application; implementation decisions, data model, limitations and unresolved items live here. Written 2026-10-07.

The standalone HTML cannot be imported into Odoo as a working store. It is a reference implementation: its layouts, copy and data model are to be recreated with Odoo pages, eCommerce categories, product records and website forms. Its JavaScript cart, filters and WhatsApp preview are prototype behaviour and must be replaced by Odoo's server-side equivalents, not copied.

One Odoo 19 page was fetched and read directly on 2026-10-07: Prices / hide prices (19.0) — retrieved 2026-10-07 ↗. It confirms that enabling Prevent Sale of Zero Priced Product (Website › Configuration › Settings › eCommerce) with a Button URL replaces Add to Cart with a Contact us button for zero-priced products — the native mechanism for this catalogue's “Request Price” products.

Shop-centred navigation model

The separate “Shop by Category” directory journey was removed. The Shop page is the only catalogue-discovery surface; departments and subcategories are filters, not pages.

Subcategory filter / breadcrumb#/shop?category={{dept}}&subcategory={{sub}}/shop/category/{{child-category}} (child of the parent)
Legacy #/categoriesreplaces history entry → #/shop301 redirect to /shop (Website › Redirects)
Legacy #/category/{{dept}}[/{{sub}}]replaces history entry → filtered Shop301 redirects to the category URLs

Browser Back/Forward work because every filter, sort and page lives in the hash query string and legacy routes use location.replace (no extra history entry, no redirect loop — tested).

Product-import considerations

  • Create the six parent eCommerce categories and 59 children first with stable external IDs; then import products referencing them. Categories & variants (19.0) ↗
  • Export a product template from the actual database to learn its column headings before building an import file; no ready-made CSV is implied by this prototype. Products (19.0) ↗
  • Import only approved records. Set zero price for quote-only products and enable the zero-price “Contact us” behaviour. Prices / hide prices (19.0) — retrieved 2026-10-07 ↗
  • Do not import sourceReference, evidenceStatus or demo prices.
  • Create Power source, Phase and (optionally) Application as attributes with “Never create variants”, otherwise every value multiplies variants.

WhatsApp workflow

One number (whatsappNumber) controls every action. Each product enquiry contains: product name, model/SKU where verified, selected quantity, displayed price or “Request Price”, public product URL, and three requests (availability, delivery to the customer's location, final quotation including taxes), ending “This is an enquiry, not an order.” The cart summary variant lists all lines and the displayed subtotal. If the number is empty or invalid the dialog shows the prepared text, a Copy button and an explanation; no wa.me link is rendered. Opening WhatsApp never produces an order or payment confirmation.

Custom In Odoo this is theme JavaScript composing a https://wa.me/<number>?text= link from the product record — it is not the Odoo WhatsApp app or an API integration.

Static-site limitations

GitHub Pages serves files only. It cannot provide server-side checkout, payment verification, live stock, customer accounts, secure form processing, CRM submission, order management or private customer records. The deployment is a catalogue: discovery, client-side search/filter, a local enquiry list, WhatsApp-first enquiries and quote requests. Forms never claim to send; the cart never claims to order.

  • WhatsApp number, phone, email, address, operating hours.
  • The approved product list with supplier SKUs, real prices, tax treatment, sale units and licensed photographs.
  • Brand authorisations for any retailer-listed brands retained.
  • Delivery coverage, charges, lead times, cross-border responsibilities.

  • Privacy notice, terms of sale, data-controller details.

Demo-to-production process

  1. Owner reviews docs/source-register.md and approves records; add their IDs to approvedProductIds.
  2. Replace demo prices with real prices (or set price: null for quote-only); set approved: true.
  3. Replace equipment.webp tiles / add per-product images; update image, gallery, alt.
  4. Fill contact fields and publicBaseUrl; set a valid whatsappNumber.
  5. Replace policy placeholder copy in app.js (POLICIES) with approved text.
  6. Set siteMode: "production"; run python3 tools/build-standalone.py; re-run the acceptance suite; check that no “demonstration” wording remains.
  7. Deploy to GitHub Pages (README).
